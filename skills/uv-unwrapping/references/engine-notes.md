# Engine notes

The rest of this skill is engine-neutral. This file holds what a specific engine does with the UVs, with sources.
Add a section when another engine is used, with its own sources, rather than writing its specifics into the body.

## Unity (2022.3, Built-in Render Pipeline; the version VRChat uses)

Sources checked 2026-10-17 unless a row says otherwise.

| Topic | Unity behaviour | Source |
|---|---|---|
| UV channels | Blender's first UV map is UV0 (textures); the second is UV1, which Unity calls `uv2` and bakes lightmaps from ("Unity stores baked lightmap UVs in its mesh in the Mesh.uv2 channel") | https://docs.unity3d.com/2022.3/Documentation/Manual/LightingGiUvs.html |
| UV channel count | 8: channels 0-7, `uv` to `uv8`. The audit flags a mesh with more UV maps | https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Mesh.SetUVs.html |
| Vertex splits | "A vertex must be split if it has multiple normals, UV coordinates or vertex colors" | https://docs.unity3d.com/2022.3/Documentation/Manual/ModelingOptimizedCharacters.html |
| Normals and tangents | Import normals from the FBX (Normals: Import) so the hard edges you baked with survive; Tangents: Calculate Tangent Space (MikkTSpace), which matches Blender's bakes | https://docs.unity3d.com/2022.3/Documentation/Manual/FBXImporter-Model.html |
| Normal map convention | Y+ ("sometimes known as OpenGL format"), which is what Blender bakes | https://docs.unity3d.com/2022.3/Documentation/Manual/StandardShaderMaterialParameterNormalMap.html |
| Mirrored islands | The bitangent sign is stored per vertex in `tangent.w`, so a normal map baked with the mirror in place shades correctly | https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Mesh-tangents.html |
| Texture wrap | With Wrap Mode Repeat, islands offset by whole tiles sample the same texels; Clamp smears them. The page lists the modes but not a default: check the texture's Wrap Mode | https://docs.unity3d.com/2022.3/Documentation/Manual/texture-type-default.html |
| Detail maps | Standard's Secondary Maps overlay a second albedo and normal map, "mapped on a much smaller scale repeated many times", for "sharp detail when viewed up close": the close-range answer for tiling surfaces players walk up to (`texel-density.md`). Detail Albedo x2 is multiplied in (Unity multiplies it by `unity_ColorSpaceDouble`, so mid grey, sRGB 128, is neutral), the Detail Normal Map is blended over the main one, the Detail Mask's alpha channel masks both, and they take their own tiling and a UV Set (UV0 or UV1: UV1 is the lightmap UV, so keep UV0) | https://docs.unity3d.com/2022.3/Documentation/Manual/StandardShaderMaterialParameterDetail.html; Unity's built-in shader source (UnityStandardInput.cginc: `Albedo`, `DetailMask`), checked 2026-10-18 |
| Lightmap UV rules | "It should be within the [0,1] x [0,1] UV space", "a wide enough margin between individual charts", "not have any overlapping faces"; lightmappers dilate chart texels, "so the UV charts of your Mesh need to be at least two full texels apart from each other to avoid light bleeding" (the source of this skill's 2-texel gap, measured at the renderer's real footprint) | https://docs.unity3d.com/2022.3/Documentation/Manual/LightingGiUvs-GeneratingLightmappingUVs.html (checked 2026-10-17) |
| Lightmap footprint | A renderer's UV2 is scaled to texels per metre x sqrt(surface area / b) x Scale In Lightmap x LOD scale texels per UV unit, b = the bounding box of all its UV2 charts together as a share of the tile, not rounded to a power of two (Unity rounds the box's longer side to whole texels). Unity packs only that chart box into the atlas, not the whole scaled tile (other renderers' boxes sat inside a renderer's tile, outside its box), so a renderer's atlas cost is (texels per metre x Scale In Lightmap x LOD scale)^2 x area, whatever its UV2 layout (24,002 vs 24,000 px2); empty space inside the box costs texels: effective density = texels per metre x sqrt(charts' area / box area). Measured exact for b 0.125-1 (0.990-1.000; a 30 x 2 m strip at b 0.125: 438 px). LODs: LOD1+ get their own atlas space at LOD scale 0.5^n (measured 0.995 / 0.492 / 0.250; Receive Global Illumination = Light Probes takes a LOD out). b = 0.85 is the planning estimate; pack UV2 gaps for b = 1. Lightmap resolution, capacity and which pieces are probe-lit: the `vrchat-lighting-and-baking` skill | Unity 2022.3.22f1 Progressive GPU bakes, 2026-10-16 (dry run, 60 texels/m, b 0.79-0.95 within 0.6%) and 2026-10-17 (packing and LOD scenes, 20 texels/m) |
| Generate Lightmap UVs | The importer's generator writes `uv2` and overwrites an authored lightmap UV: leave it off for those meshes. For one-off props it is fine with Margin Method Calculate, Min Lightmap Resolution = the scene's texels per metre x the smallest Scale In Lightmap, Min Object Scale = the smallest scale: the Manual Pack Margin is "The margin between neighboring charts (in pixels), assuming the Mesh takes up the entire 1024x1024 lightmap". Defaults: Hard Angle 88 deg, Angle Error 8%, Area Error 15%, Pack Margin 4 | https://docs.unity3d.com/2022.3/Documentation/Manual/LightingGiUvs-GeneratingLightmappingUVs.html |
| Seam stitching | Stitch Seams (Progressive lightmapper) hides seams between straight, axis-aligned chart edges | https://docs.unity3d.com/2022.3/Documentation/Manual/Lightmapping-SeamStitching.html |
| Checking a bake | Scene view draw mode UV Overlap shows overlapping lightmap texels | https://docs.unity3d.com/2022.3/Documentation/Manual/GIVis.html |
| Bakery | "Meshes must have non-overlapping UV for lightmapping. UV2 is used if present (otherwise UV1)"; its UV validation checks that lightmap UVs "lie within 0-1 range and don't overlap". By default "every LOD mesh receives a unique lightmap, taking space in the atlas" | https://geom.io/bakery/wiki/index.php?title=Manual |
| Bakery footprint | With Bakery's defaults (Alternative Scale In Lightmap off), a renderer gets a rect of side L = texels per unit x sqrt(2 x surface area x Scale In Lightmap) texels: the area is the sum of abs(cross) over its triangles (2 x the area), the UV area is ignored on purpose, and Scale In Lightmap multiplies the area (a linear factor s needs s^2). L goes to the UV2 charts' bounding box's short side and L x (long / short) to the long side, so the texel scale is L / the short side along both axes and a thin box costs its aspect times L^2. The Default atlas packer insets each rect 3 texels on every side (`texelPaddingForDefaultAtlasPacker`); xatlas does not (`texelPaddingForXatlasAtlasPacker`, default 1, between rects). No LOD factor: each LOD is sized by its own area. Pack for (L - 6) with the box filling the tile: `lightmapper="bakery"`. Effective density on the surface = footprint x sqrt(charts' UV area / surface area); the audit's gate is half the planned texels per metre. Planning, capacity and the fix: the `vrchat-lighting-and-baking` skill | Bakery's `ftBuildGraphics.cs` (`CalculateHolderUVBounds`, `ApplyAreaToUVBounds`, `Pack`, the xatlas pack) and `BakeryProjectSettings.cs`, as installed in a Unity 2022.3.22f1 project, read 2026-10-24; not measured in a bake here |
